## What changed
Still nothing in the browser, but B.AI can now answer "what do I ride?" with code alone, no AI.
`planTrip()` gives up to 3 different ways from A to B (walk → ride → transfer → ride → walk), and
`checkRoutes()` answers "is the bus to SM Fairview OK?" with yes/no and a reason. Pedro Gil Taft →
España returns the Baclaran – SM Fairview bus first (~22 min); Cubao → Ayala returns the MRT. 62 tests pass.

## How it was done
1. **Tests first.** A hand-made 9-stop network (`tests/fixtures/mini-network.ts`) where every answer
   can be worked out on paper, plus checks on the real `network.json` (acceptance tests 1–3).
2. **`params.ts`**: every guess in one place: walking 80 m/min, streets 1.3× longer than a straight
   line, speeds (train 30, bus 15, jeep 12, UV 20 km/h), radius 600 m then 1 km, costs.
3. **`prepare.ts` + `nearby.ts`**: lookup tables built once (which patterns stop at each stop, walking
   links) and a grid of ~550 m cells so "stops near me" checks a few cells, not 4,835 stops.
4. **`plan.ts`**: the search. Round 1 = best way to every stop with one ride, round 2 = two rides,
   round 3 = three. Rides only go forward. Then it bans the winning signboards and searches again to
   find *different* answers, and drops near-duplicates ("same trip plus a 300 m jeep").
5. **`match.ts` + `check.ts`**: "SM Fairview" → routes whose signboard has Fairview (accents and one
   typo forgiven; "SM" is optional). Each matched route gets a reason: passes_both, wrong_direction,
   ride_too_short, origin_only, destination_only, passes_neither, or no_such_route.
6. Eyeballed real answers with `npm run try:router` and fixed what looked silly (see below).

### Key code
The trick that makes one pass along a route enough:

```ts
// riding cost grows with distance, so the best place to have boarded is the one with the
// lowest (cost so far + penalty − minutesPerMetre × distanceAtBoarding)
const cost = boardVal + perM * p.dist[j];       // cost of getting off at stop j
if (lab) pending.push({ pos: j, v: lab.cost + penalty - perM * p.dist[j] }); // could board here
```
Walking each route once from start to end, we keep the best boarding seen so far, so every later
stop's cost is one subtraction away. That is the core idea of RAPTOR (Round-bAsed Public Transit
Optimized Router), minus the timetables we don't have.

## Why it was done this way
- **Reason for the approach:** round-based search naturally caps transfers (3 rounds = 2 transfers)
  and gives the best answer for each transfer count, which is what a commuter compares.
- **Alternatives considered:** Dijkstra over a stop graph (hard to cap transfers, easy to accidentally
  ride backwards); OpenTripPlanner (needs too much memory for free hosting, ruled out in CLAUDE.md).
- **Fixes from eyeballing real answers:** a 3-minute "boarding" cost per ride and a 500 m minimum ride
  (otherwise it suggested 100 m jeep hops), a "nested answer" filter, and a rule that an answer may
  walk at most 60% of what walking straight there would take (otherwise "ride past it and walk back").
- **Trade-offs:** times are rough (no traffic or waiting in `totalMinutes`). The data is from 2015, so
  some answers use buses that no longer run on EDSA; that's the corrections file's job, not the router's.

## Concepts to learn from this
- **RAPTOR** — a transit search that works in rounds, one per ride, instead of a general graph search.
- **Spatial grid index** — bucket points by map square so "what's near me?" only looks at nearby buckets.
- **Test fixture** — a tiny fake dataset where you know the right answer, so tests check logic, not luck.

## How to undo or tweak it
- Speeds, walking, radii, penalties, minimum ride: `lib/router/params.ts`.
- How different the 3 answers must be: `diverse()` and `nestedRides()` in `lib/router/plan.ts`.
- Words ignored or optional in signboards: `STOPWORDS` and `WEAK` in `lib/router/match.ts`.
- Try any change against real trips: `npm run try:router`.
